Does an LLM Encoder Help a Learned Financial Reranker?
A Controlled Test of Qwen3.5 Asset and Investor Embeddings on Four FAR-Trans Windows

Anastasia Shavrina (Анастасия Шаврина) · aoshavrina@edu.hse.ru · Team DimSum (with Анна Шрейбер)
Team repository: https://github.com/shavrinaanastasia/DimSum · experiment commit: @@COMMIT@@ (code in hw3/)
LLM4Rec, HSE University — Homework 3 (Test Your Project Idea), individual report · 21 November 2026

Abstract—In HW2 a LightGBM LambdaRank reranker beat every provided baseline, but its LLM investor feature added nothing. For HW3 I strengthened the reranker and gave the LLM a fairer test. The reranker is now trained on 12 monthly windows, gets 17 re-buy timing features, and its hyper-parameters were chosen on a validation month. The LLM (Qwen3.5-0.8B, role: Encoder, both on the item and on the user side) gets two chances: an asset-text embedding of all 721 asset descriptions, and the HW2 investor embedding (UMAP-32). Each has a matched control: the same features computed from a TF-IDF vector of the same text, and the same reranker without the feature. The evaluation sets and metrics were fixed before comparing methods; one preliminary D0 run is disclosed in §3.2. They are the starter's 100-user sample (T100) and the starter's full warm cohort at four cut-offs: D0 2021-06-01 (primary), D1 2021-09-01, D2 2021-12-01 and D3 2022-06-01, with 10,404–14,475 users and 4,728 future buyers in total. Result 1: the main model beats Latest buy, the strongest baseline, on every dev set. On D0 it scores 0.0546 / 0.4821 (all / nonempty) against 0.0526 / 0.4648; pooled over all four sets the nonempty gain is +0.0335, 95% CI [+0.0282, +0.0388]. Result 2 (ablation): removing the LLM features changes nonempty nDCG@10 by −0.0003 [−0.0021, +0.0016]. The LLM asset encoder against its TF-IDF control differs by +0.0000 [−0.0019, +0.0019], so any LLM effect is smaller than 0.002 in either direction. Failure analysis: the gain is largest for users with 1–4 past assets (+0.07 to +0.08) and for users whose next purchases are all new assets. The main remaining loss is that 66% of those new-asset buyers still score 0, although the candidates contain 81–90% of the new assets they bought: the problem is ranking, not retrieval.

1. Introduction

Project idea. Our team asks where an LLM can help a Top-10 asset recommender on FAR-Trans [1]. My part covers investors with a purchase history; Anna works on cold-start and sparse-history users. In HW1 I asked how much of an LLM investor embedding a recommender needs. In HW2 I found that a 2-d UMAP projection is as useful as the full 1024-d vector inside a reranker, but also that the reranker without any LLM feature scored the same (0.4782 vs 0.4798 nonempty). That left two open problems, which HW3 addresses. (i) The HW2 reranker was weak: three training months and no tuning. A null LLM result on a weak model is not convincing, and it also costs benchmark points. (ii) The LLM was tested only on the user side, and without a text control. Following the Session 3 advice to use strong baselines and matched controls, I made two changes before testing the LLM again. First, I made the non-LLM model as strong as I could, using validation data only. Second, I gave every LLM feature a control built from identical text without an LLM.

Claim tested (Session 3 template). For warm FAR-Trans investors [users], adding Qwen3.5 Encoder features (asset-text similarity to the user's portfolio and investor-profile neighbour scores) [evidence] changes nDCG@10 on 30-day future purchases [metric], relative to the same LambdaRank reranker with TF-IDF features on the same text, or with no text features [control], over four monthly cut-offs of the starter protocol [conditions]. LLM role: Encoder only; ranking is done by LightGBM, and the LLM generates no text.

2. Related Work

FAR-Trans [1] defines the data and nDCG@10 on future purchases. The course package adapts LLM-Rec [2] and LLMRank [3]: the first enriches item text with an LLM, the second uses the LLM as a zero-shot Ranker over fixed candidates. I use the LLM as an Encoder instead. PromptEOL [4] turns a decoder-only LLM into a sentence encoder by asking it to compress the input "in one word" and taking the last hidden state. I apply it both to asset descriptions and, as in HW2, to investor profiles compressed with UMAP [5]. The Session 3 slides separate candidate retrieval from evidence retrieval, as in RAG [6]. My pipeline uses only candidate retrieval: user-kNN, item-kNN, EASE [7], implicit ALS [8] and popularity. The LLM adds no retrieved evidence; it adds dense features to a LambdaMART-style ranker [9]. My text control is TF-IDF [10], computed on exactly the same asset strings.

3. Method

3.1 Pipeline (hw3/rerank3.py)

  1. Data and protocol. I call the provided data_adapter.load for users, cut-off, eligible assets (767–795), truth and popularity. Final rankings go through the provided save_results, which validates them and computes nDCG@10. The four provided baselines therefore run unchanged in the same job.
  2. Candidates (as in HW2): each user's own past buys, plus the top 50 assets from each of user-kNN, item-kNN, EASE, iALS and 90-day popularity. That is 69–158 candidates per user (median 95), restricted to eligible assets.
  3. Features (70 in the main model):
    • 45 HW2 behaviour features: repeat counts, recency, popularity and trend, returns, CBF similarity, model scores and ranks, risk fit.
    • 17 new re-buy timing features, motivated by a headroom analysis: 63–83% of future purchases are repeats. Examples are the median gap and gap CV between a user's buys of the asset, the days "due" relative to that gap, buys in the last 30/60/180 days, whether the asset was sold after its last buy, and the user's re-buy rate and new-asset share.
    • 3 asset-Encoder features: cosine between the asset and the user's 365-day decayed portfolio profile, maximum cosine to any other asset the user bought, and the profile rank.
    • 3 TF-IDF control features: identical, computed on character 3–5-gram TF-IDF of the same text.
    • 2 investor-Encoder features: the HW2 UMAP-32 neighbour score and its rank.
  4. Asset Encoder (LLM call, hw3/embed_assets.py).
    • Model: frozen Qwen/Qwen3.5-0.8B [11], revision 2fc06364715b967f1860aea9cf38778875588b17.
    • Prompt: This financial asset:\n"{text}"\nmeans in one word:". The text is "Asset: {name}; category: …; subcategory: …; sector: …; industry: …" from asset_information.csv.
    • Encoding: the last-token hidden state (1024-d, L2-normalised) for each of 721 distinct texts. It ran with fp32 on CPU, max 128 tokens, batch 16, in about 20 min, and is cached.
    • The Encoder emits vectors, not text, so no invalid output is possible. The investor vectors are the HW2 ones (Colab T4, fp16).
  5. Training without leakage.
    • Training uses 12 monthly windows before the cut-off. Each label window is [c, min(c+30 d, cut-off)), and every feature uses only rows before its own window cut-off c.
    • A window at c uses the newest investor embedding with cut-off ≤ c; otherwise the feature is missing (NaN). The earliest embedding is 2021-03-01, so the investor feature exists in only 3/6/9/12 of the 12 training windows for D0/D1/D2/D3. All test users have an embedding.
    • The most recent window is the validation split for early stopping. The model is then refit on all 12 windows with 3 seeds, and the scores are averaged.
    • Top-10 is taken by score; padding with starter popularity was never needed.

3.2 Model selection on validation only

Hyper-parameters were chosen on the D0 validation month (2021-05, inside the training data) with hw3/tune.py, tune2.py and tune_extra.py. The logs are in hw3/outputs/tune_*. The same month also serves for early stopping, so the validation scores are slightly optimistic.

Disclosure. Before tuning, I ran one preliminary comparison on D0 test truth (outputs/dev_D0_fast, feature_fraction 0.8).

  • That run's two best variants, TF-IDF and both-LLM, scored 0.4823 nonempty; main was later defined as their union.
  • D0 is therefore not a clean held-out set for choosing between my variants. D1–D3 were first evaluated only after every setting below was fixed, so they are the clean confirmation.
  • D3 was moved from 2022-03-01 to 2022-06-01 after only the baseline run at 2022-03-01, before any run of my models there.

The settings chosen:

  • LightGBM feature_fraction 0.5, chosen from a 12-setting grid: validation nDCG@10 0.6187 vs 0.6164 for the default, both 3-seed averages. The other settings are lr 0.03, 31 leaves, min_data_in_leaf 50 and truncation 20.
  • 12 training windows rather than 24 (0.6187 vs 0.6182).
  • A group of 8 extra popularity and seasonality features was rejected (0.6153 vs 0.6180, single seed).
  • The main model was fixed as all feature groups together. After the dev results I did not switch to a variant that scored higher on one dev set.

Reading Table 1. The main model beats all four baselines on every full-cohort set. Against Latest buy, the strongest baseline, every CI excludes 0, and pooled over the four sets the nonempty gain is +0.0335 [+0.0282, +0.0388]. In all-user terms that is +0.0019 (D0) to +0.0056 (D1), because only 7–11% of warm users buy in any 30-day window. Compared with my HW2 method, the main model is slightly higher on D0 (0.4821 vs 0.4798 nonempty) and slightly lower on T100 (0.0380 vs 0.0386). The HW2 numbers are copied from that report, not re-run, so I make no claim that HW3 improves on HW2. The provided LLM-Rec encoder beats its own text control on T100 (+0.0019 all-user), but it stays below Popularity and both recency baselines, and well below the main model. On T100 the main model (0.0380) beats Latest buy, Latest buy or sell and CBF with CIs above 0. Against Popularity the gain is +0.0094 all-user, but its CI includes 0, because only 11 of the 100 users have labels. With so few labels the T100 ordering of my variants (0.0355–0.0384) is noise, and it is not used for any decision.

Runtime (full D0 run, 10,404 users, not --fast): recommendation generation for all users is the cost that counts for the benchmark tie-break.

  • Recommendation generation: 348 s. Of this, test candidates and features take 318 s and scoring and Top-10 for all 10,404 users take 30 s.
  • Training: 347 s, early-stopping fit plus 3-seed refit on 12 windows of cached features. Building the training features once took about 12–15 min (60–80 s per window) before caching.
  • Whole run: 1,286 s, including the ablation variant.
  • On T100: 51 s generation, 283 s training.
  • Provided baselines: the whole starter run takes 18 s on T100.

The times above exclude the one-off asset encoding (about 20 min on CPU) and the HW2 investor encoding (78 min on a T4 for five cut-offs), both cached.

Reading Table 2. No LLM effect is detectable. Every LLM-vs-control difference is inside ±0.0006, and each CI rules out effects larger than about ±0.0027. Which variant scores highest changes from one set to the next (re-buy on D0/D1, asset-LLM on D2, both-LLM on D3), so the differences are noise. The model does use the text features. In the main model, TF-IDF receives 15–18% of the total split gain on D0–D2 (2% on D3), the LLM asset features about 1%, and the investor features 0.2–0.5%. They do not change the top of the ranking, though; my reading is that they mostly repeat item-identity information that the collaborative scores already carry. The re-buy features take 20–44% of the gain, yet they too add only +0.0010. No new feature group produces a measurable gain on its own.

A fairer test of the investor Encoder. On D0–D2 most training windows lack the investor feature, which biases its test towards null. D3 is the only set where all 12 windows have it:

  • investor features alone vs re-buy: +0.0019 [−0.0036, +0.0074];
  • both Encoders vs re-buy: +0.0050 [+0.0006, +0.0095].

The second difference is nominally significant, but it is one of many uncorrected comparisons and does not hold in the pooled analysis. I report it as a lead to test on the official set, not as a finding.

Failure modes.

  1. Heavy users. For users with 10+ past assets the main model barely beats Latest buy, and on D0 it is slightly worse. Their next buys are usually among dozens of past assets, and recency alone is already a strong ordering. The model loses to Latest buy for 20% of all nonempty users (959 of 4,728) and wins for 31% (1,489).
  2. New-asset buyers. These are 22% of buyers. The gain over Latest buy is largest here (+0.086), but 66% of them still score 0. Coverage shows the cause is ranking, not retrieval (hw3/coverage.py):
    • the candidates contain 93–98% of all future purchases and 81–90% of the new-asset purchases;
    • 89–97% of buyers have every purchase among their candidates.
    The model ranks the user's past assets above the new ones, which is right for most users but fails for these. Text similarity to the portfolio, from the LLM or from TF-IDF, did not fix this. My reading is that investors' new purchases rarely resemble their holdings by name or sector.
  3. Variation across windows. The nonempty share differs by window (7.3–11.3%), so all-user means are not comparable across cut-offs. That main beats Latest buy holds in every window. The order among my variants does not.

4.5 Verification

My personal check (one user, by hand; hw3/check_one_user.py). I took user 6FA5BF73… under main in the T100 run, the labelled user with the most future purchases. The check script was AI-written; I ran it myself, checked its filter, and did the arithmetic below by hand. It recomputes the truth directly from transactions.csv rather than through the starter's code path: Buy, 2021-06-01 ≤ t < 2021-07-01, positive transaction ID, ISIN in the starter's eligible list. That gives 6 assets, all of them bought before the cut-off too (repeats). In the saved Top-10 the hits are at ranks 1, 3 and 5 (GRS419003009, GRS260333000, GRS518003009).

  • DCG = 1 + 1/log24 + 1/log26 = 1 + 0.5 + 0.386853 = 1.886853.
  • IDCG = Σr=1..6 1/log2(r+1) = 3.304666.
  • nDCG@10 = 0.570966, equal to the starter's saved value; the saved relevant count (6) equals mine.

Other checks.

  • (a) The provided baseline rows in my runs equal stand-alone starter runs. The starter's protocol.json for each set, which holds its hash, is saved as starter_protocol.json in the corresponding run folder.
  • (b) A leakage incident was caught and fixed. A helper script once built four early training windows with an embedding newer than their cut-off. I deleted those cached frames, made the rule a single function (inv_for), and confirmed that tuning had used the correct frames.
  • (c) On D0 the --fast all-user means equal those of the full run (which builds rankings for all 10,404 users) to the last digit: main 0.054581609…, the TF-IDF variant 0.054480550…, Latest buy 0.052632821…. The T100 run uses exactly the starter's 100 user IDs, and the SHA-256 hashes of its four data files match the starter's protocol.json.
  • (d) Self-similarity is masked in the "max similarity" features, so a candidate never matches itself.

5. Discussion

What worked: a stronger learned reranker. Training on 12 windows and tuning on validation gives a method that beats every provided baseline on four independent cut-offs and the 100-user sample, with all CIs against Latest buy above 0.

What did not: the LLM. With a matched TF-IDF control and four dev sets, the Qwen3.5 asset Encoder changes nDCG@10 by 0.0000 ± 0.0019, and the investor Encoder by −0.0005 ± 0.0021. HW2 showed the same for investor embeddings with one window; HW3 extends it to item-side text and to four windows, with enough users to rule out effects above about 0.003. In this data the signal is which asset and when, not what the asset is.

Why the final model still contains LLM features: keeping or dropping them does not change the score beyond noise. I therefore keep the model I defined before D1–D3 were evaluated, rather than pick a variant by test score.

Threats to validity:

  • These are development results under the teaching protocol; the official evaluation set is not yet released.
  • D0 was seen once before tuning (§3.2).
  • Training label windows follow calendar months, so they are 28–31 days rather than exactly 30, and one overlaps the next by two days. None crosses the test cut-off.
  • The cut-offs were chosen for embedding availability.
  • Asset names in the prompt could let the LLM use knowledge from after the cut-off; the null result makes this moot here.
  • nDCG@10 measures agreement with purchases, not suitability.

Next steps: candidate generation for new-asset buyers (Anna's new-asset filler); an LLM Ranker applied only to new-asset candidates, where text is the only signal; and retrieval of evidence such as news, following the Session 3 RAG design, compared against "no extra context".
